# Requirements Analysis — Design

## 需求类型

🆕 新产品 — 本文件仅包含适用于该类型的分析内容（用户研究综合、竞品分析、优先级矩阵、核心决策）

## 商业目标

- BG-01：让后续 4 个域接入 AI 调用与会话记录时不重复建设——新增业务域的模型调用零新增密钥读取与 HTTP 客户端代码（以代码评审结论判定）
- BG-02：降低单个任务的启动成本——从任一入口到第一次获得 AI 结果 ≤ 3 步（选项目 → 给输入 → 发起调用）
- BG-03：让每次分析可追溯——成功的模型调用 100% 有 AiCallRecord，失败调用 100% 有失败状态与原因
- BG-04：让工作台可部署到非本机环境——未认证访问 100% 被登录前置校验拦截，登录口令与令牌不落日志、不以明文存储（依据 `answers.md` 2026-11-17 19:52:50 的部署形态变更）
- BG-05 与 BG-06 已迁出：BG-05（知识库闭环）迁至 `specs/knowledge-base_20261117205011`；BG-06（仓库接入闭环）迁至 `specs/repo-integration_20261117205011`（用户 2026-11-17 20:50:31 拆 spec）

## 用户研究综合（仅 🆕 新产品）

**数据现状：本阶段没有任何原始用户研究数据（无访谈记录、问卷、工单、行为埋点）。以下内容全部是基于需求原文与产品定位的假设，不是研究结论；不含编造的数字、引语或市场规模。**

目标用户画像（假设）：

- 主要角色：测试工程师。每轮迭代要产出用例、复现与定位缺陷、翻日志、写 SQL 验证数据、整理回归范围、汇总报告，六类工作频繁切换。
- 次要角色：测试负责人。关心「这个结论可信吗、谁在什么时候用什么材料得出的」，需要回看而不需要重新分析。
- 次要角色：业务域开发者（后续 4 个域的开发者）。需要一套现成的模型调用、输入落盘与会话记录能力。

## 竞品分析（仅 🆕 新产品）

> 资料性质：本节基于 4 次联网检索（2026-11-17）整理，来源多为厂商自述、联盟/评测类文章与目录页，未见独立基准测试，也未做试用对比。标注「待验证」的结论不作为采购或对标依据，实施前需复核。检索明细、来源链接与未核实项见 `requirements-analysis/competitor-research.md`。

市场分层（已核实的分类方式）：

| 类别 | 代表产品 | 能力边界 |
|---|---|---|
| 测试管理 + AI 用例生成 | Qase、Testmo、TestCollab QA Copilot、TestFiesta、TestMu AI（原 LambdaTest） | 从自然语言 / Jira 故事 / 需求文档 / 截图 / URL 生成带步骤与预期结果的用例，评审队列、需求追溯；执行能力弱 |
| 自动化执行平台 | mabl、Katalon、Testim（Tricentis）、testRigor、TestSigma、Appvance IQ、Keploy | 生成可执行脚本、自愈定位器、CI 集成；用例管理弱 |
| 可观测 / 根因分析 | Datadog、Dynatrace、New Relic（观测侧）；incident.io、Rootly、PagerDuty（事件侧）；Resolve.ai、Cleric、Traversal（独立 AI SRE） | 日志/指标/链路取证与 RCA，依赖已接入的遥测数据 |
| text-to-SQL / SQL 优化 | SQLAI.ai、BlazeSQL、AI2SQL、Vanna.ai（开源）、Metabase AI、Hex、Fabi | 自然语言→SQL、慢查询改写建议；多数只给建议、不执行验证 |

与本产品六个入口的对照：

| 入口 | 竞品覆盖情况（检索结论） | 差异化机会（待验证） |
|---|---|---|
| 用例库（原「生成测试用例」，生成能力在入口内部） | 覆盖充分（TestCollab、Qase、mabl Test Creation Agent、TestFiesta 等） | 单点能力已被商品化，不能作为唯一卖点；入口名改为「用例库」后与用例台账合并承载（AMB-019） |
| 分析 bug | 部分覆盖（mabl 宣称 autonomous root-cause analysis；Augment Code 列出的 RCA 平台） | 与用例/回归清单串联的闭环较少见 |
| 排查日志 | 覆盖充分但绑定遥测平台（Datadog/Dynatrace） | 面向「贴一段日志」的轻量自助排查，接入成本低 |
| 分析 SQL | 工具多、质量参差；多数只建议不改写验证 | 给执行计划与实际验证的少 |
| 生成回归清单 | 覆盖弱：管理类工具有追溯，但「从变更推导回归范围」不常见 | 可能是真正的空白点（仅基于本轮检索） |
| 生成测试报告 | 覆盖充分（各测试管理与自动化平台均有） | 单点不构成差异化 |

对 `workbench-core` 的策略含义：

1. 单个入口都不新；基座价值在于「同一会话里把六个入口串起来」——同一份项目上下文、同一份制品、同一条调用记录复用，这与市场分层中「管理平台 / 执行平台 / 可观测 / text-to-SQL」各自割裂的现状形成差异（待验证）。
2. 竞品普遍绑定「接入自己的数据源」（遥测、仓库、数据库连接），本产品保持「粘贴即可用」的低门槛可降低接入成本，是可用差异点（待验证）。
3. 「生成回归清单」的空白判断只来自本轮检索，可能在未覆盖的产品（如企业内部平台）中已有实现；若后续 `regression-list` 域立项，需先做针对性验证。
4. 用例台账（记录、筛选、回放）已被测试管理平台充分覆盖，不在本域正面对标，由 `test-case` 域通过导入导出衔接。

待验证 / 未能核实：

- 各厂商定价与真实能力边界：检索到的多是目录页与厂商自述，未做试用对比。
- mabl「autonomous root-cause analysis」、TestCollab 生成质量：厂商宣称，无独立评测。
- 「生成回归清单」是否真无成熟竞品：仅基于本轮检索，可能在未覆盖的产品中已有实现。

## 核心决策

### 决策 1：本 spec 只交付 `workbench-core`

- **选择**：入口编排、AI 接入、输入采集、会话与制品记录为本次范围；四个业务域各自单独走流程
- **理由**：四个域都依赖同一套模型调用与会话记录，基座先行的复用收益最大；同域并行会制造接口分歧
- **权衡**：首版用户只能看到占位页，不能完成端到端分析；需接受「先基建、后能力」的交付节奏

### 决策 2：`ai.complete` 是模型调用的唯一出口

- **选择**：所有域的模型调用都经过基座的进程内接口，由基座负责密钥读取、HTTP 调用、超时与重试、记录写入；业务域不得自行直连模型
- **理由**：BG-01 的直接落点；密钥与审计只在一个位置，避免各域口径不一
- **权衡**：基座接口成为关键路径，任何破坏性变更会同时影响四个域，需要约定向后兼容的入参扩展方式（技术方案阶段细化）

### 决策 3：会话是输入、调用、产物的唯一归属

- **选择**：Session 持有 projectId 与 entranceKey；输入以 SessionEvent、产物以 Artifact 挂到会话；调用以 AiCallRecord 挂到会话；制品按 `sessions/<sessionId>/` 隔离
- **理由**：BG-03 可追溯；跨域只需 `sessionId` 引用，不复制数据（沿用域地图「共享数据约定」）
- **权衡**：会话必须绑定项目，创建成本略高；单条记录丢失会破坏整条链路，需要外键约束与级联策略（AMB-009）

### 决策 4：未交付入口常驻可见，进入后为占位页

- **选择**：6 个入口始终展示；未交付的入口进入后展示「所属域 + 当前状态 + 返回首页」，不创建会话、不调模型；占位状态由入口配置驱动
- **理由**：入口就是产品的能力地图；按交付进度增删菜单会让用户反复重新认识产品。配置驱动避免后续接入时改代码分支
- **权衡**：首版会暴露 4 个不可用入口，需要用文案管理预期

### 决策 5：输入分三类且都挂到会话

- **选择**：文本粘贴、文件上传、项目上下文三类输入统一以「会话事件」或「项目引用」进入同一条记录链；项目上下文不复制进会话，只按 projectId 引用
- **理由**：三类输入的来源不同，但下游需要的都是「这次分析用了什么」；复制项目上下文会让同一信息出现多份，无法回溯
- **权衡**：项目上下文后续被修改时，历史会话看到的是最新值而非当时值；如需快照，需在技术方案阶段引入版本字段（已列为待验证问题）

### 决策 6：单用户登录，登录前置校验（AMB-004 修订，原定义已被推翻）

- **选择**：提供单一口令登录；除登录页与登录接口外，所有页面与接口都要求有效登录会话，未认证一律跳转登录页 / 返回 401。口令只存加盐慢哈希并以恒定时间比较；登录成功签发服务端可吊销的会话令牌（HttpOnly、SameSite=Lax，HTTPS 下 Secure），每次请求刷新 lastSeenAt、空闲 8 小时失效且无绝对上限，登出立即吊销。管理员口令由环境变量 `AW_ADMIN_PASSWORD` 提供，启动时转存为加盐慢哈希，缺失则拒绝启动；同一来源 IP 连续失败 5 次锁定 5 分钟，成功登录后计数清零。不做多账号、注册、口令找回与角色权限；数据表 owner 字段保留但固定为单用户、不参与鉴权
- **理由**：用户明确服务要部署到非本机环境（外部 MySQL / docker-compose），无登录等于把密钥配置、会话与制品暴露给同网段任意访问者；单口令登录在满足访问控制的同时不引入账号体系与多租户返工
- **权衡**：单一口令无法区分操作者，也无法按人回收权限，泄漏后需改 `AW_ADMIN_PASSWORD` 并重启；登录页与令牌校验成为所有页面的前置路径，需保证登录态检查不因缓存或静态资源绕过。口令轮换依赖重启，无法在线热更新
- **依据**：answers.md 2026-11-17 19:52:50：「打断一下，这不是本地部署的，所以需要mysql。不能只是sqllite。」及同节「用户选择：加单用户登录（推翻 AMB-004 A 的「无登录」）」；凭据来源 / 会话有效期 / 失败锁定见 answers.md 2026-11-17 19:58:08（AMB-011 ~ AMB-013 全选 A）；被推翻的原定义见 AMB-004 A（2026-11-17 18:59:58）

### 决策 7：密钥服务端加密 + 全链路掩码（AMB-005 A）

- **选择**：密钥以服务端加密存储，加密口令来自环境变量、不写入配置文件；界面、接口响应、日志与 AiCallRecord 的提示摘要一律只展示掩码
- **理由**：密钥是基座持有的最高风险数据；单一存储点 + 单一读取路径（决策 2）使掩码与轮换只需在一处实现
- **权衡**：加密口令丢失会导致已存密钥不可用，需要重新录入；环境变量方式要求部署时额外配置，不能开箱即用
- **依据**：answers.md：「AMB-005 A」

### 决策 8：输入边界以「人工填写 + 白名单」收口（AMB-006 A / AMB-007 A）

- **选择**：项目上下文由人工填写项目名、仓库地址、技术栈、需求来源与备注，不克隆仓库、不解析代码；上传仅允许 `.txt .md .markdown .log .json .yaml .yml .csv .sql`，单文件 ≤10MB、单次 ≤10 个，同名文件自动改名保留两份
- **理由**：首版的目标是「让输入有地方放、有据可查」，不是做代码理解；白名单与限值把路径穿越、超大文件与二进制污染挡在落盘之前
- **权衡**：超大日志需要用户先切分；上下文质量依赖人工填写，回答质量可能不如带代码索引的方案（H5 待验证）；自动改名会让同名文件出现多份，需要靠时间与大小区分
- **依据**：answers.md：「AMB-006 A」「AMB-007 A」
- **2026-11-17 20:33:31 修订已迁出**：项目上下文绑定云效 / GitHub 仓库与按需读文件的修订随需求迁至 `specs/repo-integration_20261117205011`（原决策 15 ~ 17）；本 spec 保留「人工填写 + 不克隆、不建索引」口径

### 决策 9：调用失败只重试不换模型（AMB-008 A）

- **选择**：单次调用超时 120s；仅网络错误与 5xx 自动重试 1 次；最终失败写失败 AiCallRecord 并向调用方抛出可读错误；不自动切换模型。提供商「连接测试」独立使用 10s 超时（AC-003-3）
- **理由**：换模型会让调用记录无法解释「这条结论到底由哪个模型产生」；重试 1 次足以覆盖瞬时网络抖动
- **权衡**：长文本分析在 120s 内未完成会被判超时，需要用户拆小输入；国内厂商若不返回规范 5xx，重试可能不触发
- **依据**：answers.md：「AMB-008 A」

### 决策 10：永久保留 + 手动级联删除（AMB-009 A）

- **选择**：会话、事件、制品与调用记录默认永久保留；仅支持用户手动删除整个会话，删除时级联清理其事件、制品文件与调用记录；不做自动过期、归档与压缩
- **理由**：可追溯是本产品的核心价值，自动清理会破坏历史回溯；删除粒度定为「整个会话」可避免留下孤儿制品
- **权衡**：磁盘会持续增长，需要部署方自行备份与清理；不支持只删单条事件或单个制品
- **依据**：answers.md：「AMB-009 A」
