# Requirements Analysis — Design

## 需求类型

➕ 功能新增 — 本文件包含商业目标、优先级矩阵、核心决策与迁入假设；不含用户研究与竞品分析（intake 已判定跳过）。

## 商业目标

- BG-05: 打通知识库「导入 → 浏览 → 注入」闭环——让分析调用基于项目真实的术语、实体、规则与流程。可量化口径：5 个用户故事共 24 条 AC 与 7 条 EARS 全部通过；每次使用注入的调用 100% 可在 AiCallRecord 与 SessionEvent 中回查到知识库名、版本、编号列表与字符数（不含正文）；导入失败 0 残留、超限 0 截断、日志 0 正文泄露。

## 用户研究综合（跳过）

本 spec 为既有产品规划内的功能新增（intake 判定），不重跑市场研究。迁入的假设原文：

- **H6**：按编号注入知识库条目，比用户临时复述业务定义更省时、更准确（未验证，需真实使用数据；本期以 AC 与调用记录可回查性作为替代证据）。

待验证问题（不编造数字或引语）：真实使用中单次注入平均勾选多少条、注入后回答质量的差异——均无原始数据，留待上线后从 AiCallRecord 的 `knowledge_injection` 快照统计。

## 优先级矩阵

### Must Have（P0）

| 功能 | 理由 |
|------|------|
| US-012 导入知识库并建立编号索引（含 AC-012-6 项目上下文关联展示） | 闭环入口；没有导入就没有后续浏览与注入，且导入边界与回滚是安全底线（RISK-018 / RISK-019） |
| US-013 浏览与检索条目 | 「按编号确认业务概念与代码落点」是注入前的信任基础；没有浏览无法判断该不该注入 |
| US-014 会话内按编号注入 | 闭环价值所在；预算校验、留痕与脱敏在此收口 |

### Should Have（P1）

| 功能 | 理由 |
|------|------|
| US-015 新鲜度与版本冲突 | 防止把过期定义当事实；AMB-016 已定「只提示不阻断」，缺失时显示「未知」 |
| US-016 删除知识库 | 资产管理必需；删除语义（历史不变、编号标「知识库已删除」）需在首版就定死，避免事后改历史数据 |

### Could Have（本期不做）

| 功能 | 理由 |
|------|------|
| 导入报告后续回看入口 | AC 只要求导入结果展示；详情接口已保留 `importReport`，需要时可由交互设计补充 |
| 知识库版本对比视图 | 冲突只要求列出来源；逐条 diff 价值高但非闭环必需 |

### Won't Have（明确排除）

| 功能 | 理由 |
|------|------|
| 在线编辑条目、服务端路径引用 | 知识库是外部工具产出的只读资产（决策 11） |
| 代码级新鲜度校验（克隆 / 解析代码） | AMB-006 修订后仍不克隆仓库、不解析代码；归 repo-integration |
| 向量检索 / RAG / 代码索引 | 检索升级路径留待技术方案；本期 `LIKE` 够用 |

| 自动过期清理、归档压缩 | AC-016-3 明确永久保留 |
| 多用户 / 角色权限 | 继承 workbench-core 单用户登录边界 |

## 核心决策

### 决策 11：知识库是只读参考层（承接）
- **选择**：工作台只读消费 `ontology-builder-native` / `ontology-consumption` 的产出（`index.json` + `.md`），不在线编辑、不改写上传文件。
- **理由**：知识由外部工具与人工确认产生，工作台负责引用而非生产；避免双写与事实源分裂。
- **权衡**：修正知识必须在本地重新生成并重新导入（同名生成新版本），工作台内无法直接改错。

### 决策 12：`index.json` 是唯一索引，`.md` 仅提供正文（承接）
- **选择**：条目、类型、摘要、结构化字段与邻居全部来自 `index.json`；`.md` 只按编号匹配正文，匹配不上则用摘要并标「正文缺失」。
- **理由**：索引与正文解耦，缺失正文不影响浏览、检索与注入（降级为摘要）。
- **权衡**：`.md` 与编号匹配失败时信息量下降，但不会以空内容冒充正文。

### 决策 13：注入计入 200,000 字符全局上限（承接，用户已定）
- **选择**：注入正文与提示正文合计 ≤200,000 字符；超限拒绝调用并显示分段字数与上限，不截断。常量由 workbench-core 单点定义（`AW_PROMPT_MAX_CHARS`），本 spec 引用同值、不重复定义。
- **理由**：与文本粘贴上限同口径，避免两套预算；唯一校验点在 core 的 `AiGateway.complete`，本 spec 只产出注入块与分段字数。
- **权衡**：超长提示 + 大量勾选会被整体拒绝，用户需减少条目或缩短提示；选择器实时显示字数以降低摩擦。

### 决策 14：本体生成拆分为独立域（承接）
- **选择**：`ontology-builder-native` 内嵌、人工确认对话框不在本 spec；后续复用 core 的 AI 网关、会话、事件、制品与人工确认能力。
- **理由**：生成与消费是两条能力线，拆分后本 spec 可独立交付最小闭环。
- **权衡**：本期用户需在工作台之外运行工具；后续由 `ontology-builder` 直连推送替代手工上传（扩展计划）。

### 决策 15：复用 workbench-core 外壳与依赖（本 spec 新增，用户已定）
- **选择**：知识库入口放侧边栏「基座管理」分组（`/knowledge-bases`），注入内嵌在会话调用面板；AppShell、设计 token、登录态、AI 网关、`sessions.*`、`artifacts.save`、凭证加密全部复用，不重复实现。
- **理由**：用户在 2026-11-17 21:00:28 拆分归属决策中明确「复用 workbench-core 外壳」；单用户登录边界不变。
- **权衡**：知识库页面的信息密度受既有外壳约束；跨 spec 依赖需要 core 先提供挂载位与接口（见「待技术方案」）。

### 决策 16：不重跑市场与竞品研究（本 spec 新增）
- **选择**：沿用父 spec 已完成的产品级结论，本阶段只做范围裁剪、编号保留与跨 spec 边界约束。
- **理由**：同一产品的功能新增，重跑会得出相同结论并拖延交付。
- **权衡**：若知识库的定位发生变化（例如从项目资产变成组织资产），需要重新评估——当前无此信号。

### 决策 17：知识库存储与会话制品隔离（技术默认，待技术方案确认）
- **选择**：`knowledge-bases/<kbId>/` 独立根，与会话制品 `sessions/` 平级；独立白名单与限额，不复用会话上传面板。
- **理由**：两套白名单与上限不同（AMB-014 vs core 的会话上传口径），复用会误导用户并放大越权写盘面（RISK-018）。
- **权衡**：多一套目录与清理逻辑（启动扫描、`.trash`）；由技术方案确认最终布局与删除事务边界。

### 决策 18：失效条目剔除后阻塞式确认（本 spec 新增，2026-11-18 用户拍板）
- **选择**：发起外部请求前剔除失效条目（已删除 / 已被取代 / 不存在），弹出阻塞式确认列出被剔除编号；确认后其余有效条目照常注入并产生 AiCallRecord，取消则不发起调用且不产生 AiCallRecord。
- **理由**：原 AC-014-4 两句互斥；取「其余有效条目不受影响」保留可用性，用阻塞确认消除「静默换掉注入集合」的风险。
- **权衡**：每次存在失效条目都会多一次确认；换来的结果是用户始终知道本次实际注入了哪些条目。

## 迁入假设与待技术方案项

### 假设

- **H6**：按编号注入减少重复粘贴、提高定义一致性（未验证，见「用户研究综合」）。

### 待技术方案（原标注，本次不编造结论）

1. 登录 / 多用户 / 权限：当前继承 core 的单用户边界，迁出后是否变化未定。
2. 检索大数据量下的分页方式与 FTS 升级时机（现有结论：`LIKE` + `limit 50 / 上限 200` + cursor）。
3. 知识库与项目上下文页的耦合：`ProjectContext` 归属需与 workbench-core 协商（知识库只引用 `projectId`）。
4. 注入字符计数的「提示」部分由 core `ai.complete` 唯一校验；若知识库独立部署，进程内接口归属未定（现结论：`PreparedPrompt` 交给 `AiGateway`）。
5. 上游 `index.json` 尚无条目级新鲜度字段，「可能过期」仅在用户提供 `freshness_at` / `updated_at` 时生效（原样保留）。
6. 导入报告行号为「尽力而为」（定位 `"id": "<code>"` 首次出现位置换算行号，找不到回退 `entries[<index>]`）。
7. `index.json` 具体字段与向下兼容策略、检索服务端 / 前端、`.md` 与条目匹配规则、存储布局与删除事务边界、注入块最终拼装格式：`_handoff/from-tech-arch.md` 第 1~7 节已有技术结论但**尚未实现**，需在 tech-arch / tech-design 复核确认。

### 已确认的新增口径（2026-11-18 10:44:10，用户「全按建议」）

- **AMB-026 失效条目**：剔除失效条目 + 阻塞式确认后继续——发起外部请求前剔除失效条目并弹出阻塞式确认、列出被剔除的具体编号，用户确认后其余有效条目照常参与调用并产生 AiCallRecord，取消则不发起调用且不产生 AiCallRecord。由此改写 AC-014-4（保留原编号）：原条文的「其余有效条目不受影响」与「不产生 AiCallRecord」互斥，取前者并补阻塞确认，避免静默降级。
- **AMB-027 条目数上限**：不另设条目数上限，仅受 200,000 字符合计与条目可用性约束；若后续性能需要收口，由技术方案给出可配置阈值。
